# موتور جست‌وجوی بولی فارسی روی مجموعه اسناد ایرانداک

این پروژه یک موتور جست‌وجوی کوچک برای مجموعه‌ای از اسناد فارسی ایرانداک پیاده‌سازی می‌کند. هدف آن آماده‌سازی متن فارسی، مقایسه توکن‌سازی مبتنی بر فاصله و توکن‌سازی زیرواژه‌ای BPE، ساخت ایندکس وارون و اجرای بازیابی بولی و جست‌وجوی عبارت است.

پیاده‌سازی در قالب نوت‌بوک `Boolean_Search_Engine.ipynb` انجام شده است.

## قابلیت‌ها

- بارگذاری مجموعه اسناد از فایل JSON و تولید شناسه یکتا برای هر سند
- استخراج عنوان، چکیده، نویسندگان، کلیدواژه‌ها و تعدادی از اطلاعات فراداده
- نرمال‌سازی متن فارسی و استانداردسازی نویسه‌های عربی و فارسی
- توکن‌سازی با دو روش:
  - **Space Tokenizer:** جداسازی واژه‌ها بر اساس فاصله
  - **BPE Tokenizer:** تقسیم واژه‌ها به زیرواژه‌ها با استفاده از کتابخانه `tokenizers`
- مقایسه دو روش توکن‌سازی از نظر اندازه واژگان، میانگین تعداد توکن در سند و طولانی‌ترین توکن
- حذف اختیاری واژه‌های توقف با استفاده از فهرست واژه‌های توقف Hazm
- اجرای زنجیره پردازش واژه شامل ریشه‌یابی و Lemmatization
- ساخت Inverted Index همراه با فراوانی واژه و موقعیت وقوع آن
- ذخیره ایندکس‌ها در قالب JSON
- پشتیبانی از عملگرهای بولی `AND`، `OR` و `NOT` و پرانتز
- پشتیبانی از Phrase Query با استفاده از موقعیت توکن‌ها
- بازگرداندن شناسه و عنوان اسناد بازیابی‌شده

## ساختار ورودی

ورودی برنامه فایل `IranDoc_Data.json` است. فایل باید یک آرایه از رکوردهای JSON باشد. هر رکورد می‌تواند شامل فیلدهای زیر باشد:

| فیلد ورودی | توضیح |
|---|---|
| `title` | عنوان سند |
| `abstract` | چکیده یا متن سند |
| `authors` | نویسندگان |
| `keywords` | کلیدواژه‌ها |
| `publication_year` | سال انتشار |
| `degree` | مقطع تحصیلی |
| `document_type` | نوع سند |
| `advisor` | استاد راهنما |
| `url` | نشانی سند |
| `doi` | شناسه DOI |

فیلدهای اختیاری در صورت نبودن با رشته خالی جایگزین می‌شوند. برای هر رکورد، شناسه‌ای بر اساس ترتیب آن در فایل تولید می‌شود؛ برای نمونه `document_001`، `document_002` و مانند آن.

در ساخت متن قابل جست‌وجو، سه فیلد `title`، `abstract` و `keywords` به هم متصل می‌شوند. اطلاعاتی مانند نویسنده، سال، استاد راهنما و URL در متن ایندکس‌شده وارد نمی‌شوند.

## پیش‌نیازها

کتابخانه‌های مورد استفاده در نوت‌بوک:

- `hazm` برای Lemmatization و فهرست واژه‌های توقف فارسی
- `tokenizers` برای آموزش و استفاده از مدل BPE
- `snowballstemmer` به‌عنوان وابستگی نصب‌شده در محیط؛ در نسخه فعلی نوت‌بوک استفاده از آن به‌عنوان Stemmer فعال نیست و خط مربوط به آن کامنت شده است.
- کتابخانه‌های استاندارد پایتون مانند `json`، `pathlib`، `re`، `html`، `unicodedata` و `string`

نصب وابستگی‌ها در سلول اول نوت‌بوک انجام می‌شود:

```bash
pip install hazm tokenizers snowballstemmer
```

## آماده‌سازی و اجرا

### ۱. قرار دادن فایل داده

فایل `IranDoc_Data.json` را در مسیر کاری نوت‌بوک قرار دهید. در صورت استفاده از مسیر دیگری، هنگام فراخوانی تابع `run_pipeline` مسیر فایل را مشخص کنید.

### ۲. اجرای نوت‌بوک

نوت‌بوک را در محیطی مانند Jupyter Notebook یا Google Colab باز کنید و سلول‌ها را به ترتیب اجرا کنید. سلول اول وابستگی‌ها را نصب می‌کند.

### ۳. اجرای Pipeline

در انتهای نوت‌بوک، pipeline با تنظیمات زیر اجرا می‌شود:

```python
pipeline = run_pipeline(vocab_size=2000)
```

تابع `run_pipeline` مراحل زیر را انجام می‌دهد:

1. خواندن فایل JSON و استخراج فیلدهای اسناد
2. تولید `doc_id` و ذخیره اسناد پردازش‌شده
3. ترکیب عنوان، چکیده و کلیدواژه‌ها و نرمال‌سازی متن
4. آموزش BPE Tokenizer با اندازه واژگان درخواستی
5. مقایسه Space Tokenizer و BPE Tokenizer
6. ساخت ایندکس مستقل برای هر روش توکن‌سازی
7. ذخیره ایندکس‌ها روی دیسک
8. محاسبه آمار ایندکس‌ها
9. ساخت نمونه‌های `SearchEngine` برای جست‌وجو با هر tokenizer

برای تغییر مسیر داده یا پوشه خروجی می‌توان از پارامترهای تابع استفاده کرد:

```python
pipeline = run_pipeline(
    dataset_path="IranDoc_Data.json",
    output_dir="search_engine_output",
    vocab_size=2000,
    remove_stopwords=False
)
```

پارامتر `remove_stopwords` به‌صورت پیش‌فرض `False` است؛ بنابراین واژه‌های توقف در ایندکس باقی می‌مانند. این انتخاب به حفظ امکان Phrase Query کمک می‌کند.

## مراحل پردازش متن

### ۱. Normalization

تابع `normalize_text` عملیات زیر را انجام می‌دهد:

- تبدیل موجودیت‌های HTML به نویسه متناظر
- اعمال Unicode Normalization از نوع NFC
- تبدیل حروف انگلیسی به حروف کوچک با `casefold`
- یکسان‌سازی برخی نویسه‌های عربی و فارسی، از جمله `ي` به `ی` و `ك` به `ک`
- تبدیل ارقام انگلیسی و عربی به ارقام فارسی
- حذف اعراب و نشانه‌های ترکیبی
- حذف URLها
- حذف علائم نگارشی انگلیسی و فارسی
- تبدیل نیم‌فاصله به فاصله معمولی
- حذف نویسه‌های ZWJ و BOM
- یکسان‌سازی فاصله‌های متوالی

### ۲. Tokenization

در روش Space، متن با فاصله‌ها به واژه‌ها تقسیم می‌شود. در روش BPE، ابتدا متن‌های نرمال‌شده برای آموزش مدل استفاده می‌شوند و سپس کتابخانه `tokenizers` متن را به زیرواژه‌ها تقسیم می‌کند. در این پیاده‌سازی، `WhitespaceSplit` به‌عنوان پیش‌توکن‌ساز BPE استفاده شده است.

اندازه واژگان BPE در اجرای پیش‌فرض ۲۰۰۰ است. این مقدار از طریق پارامتر `vocab_size` قابل تغییر است.

### ۳. Stopword Handling

فهرست واژه‌های توقف از `hazm.stopwords_list()` گرفته می‌شود. حذف واژه‌های توقف اختیاری است و در اجرای پیش‌فرض انجام نمی‌شود؛ زیرا حذف آن‌ها می‌تواند اطلاعات لازم برای Phrase Query را از بین ببرد.

### ۴. Lemmatization و Stemming

تابع `transform_tokens` ابتدا واژه‌های توقف را در صورت فعال بودن گزینه حذف می‌کند؛ سپس برای هر واژه این دو مرحله را اجرا می‌کند:

1. **Lemmatization:** استفاده از `Lemmatizer` کتابخانه Hazm. در صورت خروجی دارای `#`، بخش پیش از `#` انتخاب می‌شود.
2. **Stemming:** استفاده از کلاس `RuleBasedPersianStemmer` که پسوندهای تعریف‌شده را حذف می‌کند و برای تعدادی از جمع‌های مکسر از فرهنگ استثنا استفاده می‌کند.

بنابراین در نسخه فعلی، دو مرحله Lemmatization و Stemming پشت سر هم اجرا می‌شوند؛ خروجی نهایی این زنجیره برای ساخت ایندکس و پردازش Query به کار می‌رود.

## ساختار ایندکس

برای هر tokenizer یک ایندکس وارون جداگانه ساخته می‌شود:

- `index_space.json`
- `index_bpe.json`

ساختار کلی هر ایندکس شامل سه قسمت است:

- `meta`: تعداد اسناد، تعداد کل توکن‌ها، اندازه واژگان و نوع tokenizer
- `documents`: اطلاعات خلاصه اسناد شامل عنوان، نویسنده و سال
- `inverted_index`: نگاشت هر واژه به فهرست اسناد حاوی آن واژه

هر Posting شامل موارد زیر است:

| فیلد | توضیح |
|---|---|
| `doc_id` | شناسه سند |
| `tf` | تعداد تکرار واژه در سند |
| `positions` | موقعیت‌های وقوع واژه در توالی توکن‌های سند |

ذخیره موقعیت‌ها امکان بررسی توالی دقیق توکن‌ها را برای Phrase Query فراهم می‌کند.

## Boolean Retrieval

کلاس `BooleanParser` عبارت ورودی را به ساختار نحوی تبدیل می‌کند. سپس کلاس `SearchEngine` با استفاده از ایندکس وارون، مجموعه اسناد منطبق با عبارت را محاسبه می‌کند.

عملگرهای پشتیبانی‌شده:

| عملگر | عملکرد |
|---|---|
| `AND` | اشتراک مجموعه اسناد دو عبارت |
| `OR` | اجتماع مجموعه اسناد دو عبارت |
| `NOT` | متمم مجموعه اسناد عبارت نسبت به کل اسناد |

اولویت عملگرها در Parser به این صورت است:

1. `NOT`
2. `AND`
3. `OR`

پرانتز برای تغییر ترتیب ارزیابی عبارت‌ها پشتیبانی می‌شود. نام عملگرها بدون حساسیت به بزرگی و کوچکی حروف شناسایی می‌شود.

### نمونه Queryها

```text
بازیابی AND اطلاعات
یادگیری AND ماشین
بازیابی AND NOT وب
(معنایی OR عصبی) AND بازیابی
(دانشگاه OR پژوهشگاه) AND مقالات
```

## Phrase Query

Phrase Query با بررسی موقعیت توکن‌ها انجام می‌شود. صرف وجود همه واژه‌ها در یک سند کافی نیست؛ موقعیت توکن‌ها باید متوالی و مطابق ترتیب عبارت باشند.

نمونه‌ها:

```text
"بازیابی اطلاعات"
"هوش مصنوعی"
```

در پیاده‌سازی، جست‌وجوی عبارت از همان قابلیت تطبیق توالی توکن‌ها در `sequence_search` استفاده می‌کند. از آنجا که موقعیت توکن‌ها در Posting ذخیره شده‌اند، امکان بررسی توالی و ترتیب واژه‌ها وجود دارد.


## آمار اجرای ثبت‌شده

خروجی ذخیره‌شده در نوت‌بوک برای مجموعه ۱۰۰ سندی به صورت زیر است. این اعداد مربوط به اجرای ثبت‌شده با `vocab_size=2000` و تنظیم پیش‌فرض `remove_stopwords=False` هستند.

### مقایسه Tokenizerها

| معیار | Space Tokenizer | BPE Tokenizer |
|---|---:|---:|
| اندازه واژگان مشاهده‌شده در کل مجموعه | 3914 | 1806 |
| میانگین تعداد توکن در هر سند | 378.59 | 451.19 |
| طولانی‌ترین توکن | `انگیزشدرونیانگیزشبیرونیو` | `intelligence` |
| طول طولانی‌ترین توکن | 24 | 12 |
| اندازه واژگان مدل | — | 2000 |

اندازه واژگان مشاهده‌شده در پیکره با اندازه واژگان مدل BPE یکسان نیست. همچنین BPE با وجود کاهش تعداد توکن‌های یکتا، به دلیل تقسیم برخی واژه‌ها به چند زیرواژه، میانگین تعداد توکن بیشتری در هر سند ایجاد کرده است.

### آمار ایندکس‌ها

| معیار | Space Index | BPE Index |
|---|---:|---:|
| تعداد اسناد | 100 | 100 |
| اندازه واژگان ایندکس | 3244 | 1524 |
| تعداد Postingها | 16566 | 19479 |
| مجموع وقوع توکن‌ها | 37773 | 46700 |
| اندازه فایل ایندکس | 2,318,552 بایت | 2,697,156 بایت |
| اندازه تقریبی فایل | 2264.21 کیلوبایت | 2633.94 کیلوبایت |

توجه شود که Vocabulary Size در جدول مقایسه Tokenizerها قبل از اعمال زنجیره Lemmatization و Stemming محاسبه شده است؛ در مقابل، اندازه واژگان ایندکس بعد از اعمال پیش‌پردازش محاسبه می‌شود. به همین دلیل این دو مقدار برای یک tokenizer لزوماً برابر نیستند.

## فایل‌های خروجی

پس از اجرای pipeline، پوشه `search_engine_output` ساخته می‌شود و فایل‌های زیر در آن قرار می‌گیرند:

| فایل | توضیح |
|---|---|
| `parsed_documents.json` | اسناد استخراج‌شده همراه با `doc_id` و فیلدهای اصلی |
| `bpe_tokenizer.json` | مدل آموزش‌دیده BPE |
| `index_space.json` | ایندکس وارون مبتنی بر Space Tokenizer |
| `index_bpe.json` | ایندکس وارون مبتنی بر BPE Tokenizer |

همچنین خروجی تابع `run_pipeline` شامل آمار Tokenizerها، مسیر فایل‌های ایندکس، آمار ایندکس‌ها و اشیای Search Engine است.

نمونه دسترسی به موتورهای جست‌وجو:

```python
space_engine = pipeline["search_engines"]["space"]
bpe_engine = pipeline["search_engines"]["bpe"]
```

برای اجرای جست‌وجوی بولی:

```python
results = space_engine.boolean_search(
    "یادگیری AND ماشین"
)

print(prepare_results(results))
```

برای دریافت رکورد اصلی یک سند با شناسه آن:

```python
document = space_engine.get_document("document_001")
print(document)
```

## نکات و محدودیت‌ها

- این پروژه یک موتور بازیابی بولی است و رتبه‌بندی نتایج بر اساس میزان ارتباط یا امتیازدهی انجام نمی‌دهد.
- جست‌وجو روی ترکیب عنوان، چکیده و کلیدواژه‌ها انجام می‌شود؛ اطلاعات نویسنده و سایر فراداده‌ها در متن قابل جست‌وجو وارد نشده‌اند.
- خروجی Stemmer قانون‌محور به فهرست پسوندها و قواعد تعریف‌شده وابسته است؛ بنابراین احتمال بیش‌ریشه‌یابی یا کم‌ریشه‌یابی وجود دارد.
- BPE به‌تنهایی Lemmatization یا Stemming انجام نمی‌دهد. در این پروژه، پیش‌پردازش واژگانی پیش از BPE اعمال می‌شود.
- خروجی‌های دو tokenizer لزوماً از نظر تعداد توکن یا اندازه ایندکس یکسان نیستند.
- در نسخه فعلی، Stopword Removal به‌صورت پیش‌فرض غیرفعال است.
- برای ارزیابی کمی کیفیت بازیابی مانند Precision و Recall به مجموعه Queryها و اسناد مرتبطِ برچسب‌گذاری‌شده نیاز است. صرف اجرای چند Query نمونه، معیار کامل ارزیابی کیفیت نیست.
- هنگام فعال‌کردن `remove_stopwords=True`، لازم است تنظیم حذف واژه‌های توقف در مرحله ساخت ایندکس و در زمان پردازش Query یکسان باشد.
